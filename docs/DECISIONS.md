| ADR-009 | Classify metadata-empty DOS ZIP entries as regular files | Approved for M2-02 | The architect approved a narrow fallback: accept only `System::Dos`, zero external attributes, no directory marker, and `is_file() == true`. The exception matches ordinary files in the pinned GitHub `frontend-design` archive. |
| ADR-010 | Internal Codex directory commit uses platform no-replace rename | Approved for M2-04 at `bd66e51` | The internal commit engine prepares a private directory on the destination filesystem and requests Linux `renameat2(RENAME_NOREPLACE)`, macOS `renameatx_np(RENAME_EXCL)`, or Windows `SetFileInformationByHandle(FileRenameInfoEx)` with replacement disabled. It fails closed if the required primitive is unavailable. The architect accepted M2-04 at commit `bd66e51f7c33f2955ee068532f2cb4b59ab6b593`; the squash merge is `5c10d61516fbb692f096205a9a147be3ea6bd16f`. This provides complete-directory visibility and no-clobber at final commitment, not coordinated rollback or crash recovery. |
| ADR-011 | Schema-v1 Codex project receipts use deterministic path identity and canonical inventory digests | Approved for M2-05 at `fc2d92a` | Receipt filenames hash the length-prefixed canonical project path, agent, and canonical resource ID under a domain separator. Strict JSON records include the distinct skill directory name, source provenance, project filesystem identity, complete bounded sorted file/directory inventory, and a domain-separated SHA-256 digest with explicit path and file-length boundaries. Storage uses exclusive temporary files, an exclusive writer reservation, no-replace publication, no-follow reads, and supported durability synchronization. Receipts are ownership claims, not publisher authenticity or deletion authorization. See [receipt design](receipts.md). |
| ADR-012 | Internal installs use an append-only operation journal and OS-backed store lock | Approved for M2-06 at `a711b522f6c8a7db221ac43cfd281788e25d1f91` | A versioned application-data journal records operation identity, strict schema-v1 receipt intent, destination/staging filesystem identities, operation-created inventory, and ordered state transitions. Recovery opens the receipt store, acquires and validates the persistent `.writer.lock`, and only then reads bounded journal snapshots; the lock remains held through recovery and result determination. Installation admission also reads and validates journals under its reservation lock and fails closed if any operation remains after the preceding recovery attempt. The reservation stays held through preparation, project commit, receipt publication, and journal cleanup. Recovery trusts neither receipt nor journal alone, verifies exact identities and hashes, and preserves uncertain content. Windows directory-entry flush limitations and lack of cross-filesystem power-loss atomicity are explicit. M2-07 exposes this approved boundary only through Codex project installation; remove and update remain out of scope. See [recovery protocol](recovery.md). |
| ADR-013 | Receipt-backed Codex project skill removal requires installation-time destination identity | Proposed for M3-01; pending independent architectural re-review | New installations use backward-compatible receipt schema v2, which requires the final committed destination volume/object identity and binds it into the versioned content digest. The install operation journal remains schema v1 and starts with the existing v1 receipt intent; after no-replace commit it durably advances to a v2 receipt only while recording the identity obtained from the secure destination handle. No v2 receipt is published and no install success is reported before that snapshot. Existing schema-v1 receipts remain byte-for-byte unchanged and listable, but automatic removal refuses them; THRN never derives missing ownership from a directory observed during removal. Existing interrupted install journals remain readable under their original identity and inventory checks, and recovery never rewrites an already-published v1 receipt. Removal requires v2 evidence, verifies it before quarantine planning, and revalidates the same identity at every destructive boundary. A separate versioned removal record captures the receipt, parent, destination, and per-object identities before mutation; records state transitions and per-object cleanup intents; moves the destination to operation-private sibling quarantine with no-replace rename; removes only verified receipt-listed files and empty recorded directories; and retires the receipt after content removal is established. Recovery rolls back only before deletion begins and only if the full original tree is intact; after any cleanup intent it advances only when every remaining object is still provable. Nonterminal legacy removal journals lacking install-time evidence fail closed and remain preserved. The existing `.writer.lock` serializes installation, removal, and recovery through completion. Windows directory-entry metadata cannot currently be flushed with the existing handle layer; no cross-filesystem/power-loss atomicity is claimed. See [receipt design](receipts.md) and [recovery protocol](recovery.md). |
| ADR-014 | Receipt-backed Codex project skill update uses a separate journal, old-version backup, and no-replace receipt transition | Proposed for M3-02; not approved | Update accepts one exact canonical catalog ID only when a schema-v2 receipt proves the same Codex project installation and the complete live inventory, file identities, lengths, and hashes verify. The validated local catalog must retain the same resource ID, GitHub owner/repository, source directory, and installed skill name, and pin a different full commit. No catalog refresh or caller-supplied source is used. A typed immutable `UpdatePlan` captures the old receipt/installation proof, replacement stage inventory, file-level diff, intended stage/backup paths, commit-time assumptions, and receipt transition including the old receipt file identity and raw-byte digest. A distinct schema-v1 update journal in application-data `updates` records both inventories and directory identities, old/new receipt contents, receipt temp/backup identities, operation-owned names, states, and per-object cleanup intents. Under the shared OS-backed `.writer.lock`, THRN stages the complete replacement beside the destination, rehashes it, records its identity, moves the verified old tree to an operation-owned backup with a no-replace rename, and commits the replacement to the original destination with a second no-replace rename. This is not an atomic swap. The receipt filename remains deterministic and common to old/new versions. THRN preserves the exact old receipt in a no-replace operation backup and publishes the new schema-v2 receipt through the existing no-replace publication API; unchecked receipt overwrite is prohibited. Installed listing holds the lock while reading and fails closed while any lifecycle journal is pending, preventing display of an incomplete receipt transition. Recovery is idempotent and verifies full trees, object IDs, raw receipt bytes, active receipt, and destination identity. A `Prepared` record may terminate as rolled back only when the old install/receipt remain exact and no stage/backup exists; once replacement staging has a journaled identity recovery proceeds forward. Before cleanup, a future implementation could add verified rollback only if old backup and replacement can both be positively identified; this implementation chooses forward recovery. After any old-backup cleanup intent, only strict forward recovery is allowed; missing objects require their matching durable cleanup intent. Recovery never adopts a directory from matching hashes alone or recursively deletes a backup. The old receipt is retained until the new tree/receipt verify and old-tree cleanup is complete, then removed under its own durable cleanup intent. A crash after receipt publication but before the next journal snapshot is recoverable only when the new receipt identity/contents and old backup match the journal; an unrecorded receipt temp is preserved and requires inspection. Linux/macOS synchronize files and containing directories where supported. Windows directory-entry metadata cannot currently be flushed through the secure handle layer, and no cross-filesystem power-loss atomicity is claimed. See [receipt design](receipts.md) and [recovery protocol](recovery.md). |

| ADR-015 | Explicit Codex project and user skill scopes share one validated lifecycle and OS path resolver | Approved for M3-04 | Project scope remains the default and targets `<canonical-project>/.agents/skills/<skillName>`. Explicit `--scope user` targets `<validated-user-home>/.agents/skills/<skillName>`; it is never inferred from existing files and cannot be combined with `--project`. User operations resolve their root from the OS home environment (`HOME` on Unix-like systems, `USERPROFILE` on Windows, with the platform home-directory API as fallback), never from the current working directory. A typed `ResolvedScope` is shared by install, check, update, removal, receipt matching, and recovery. THRN centralizes home, application configuration, application data, and catalog-cache paths. Existing OS-standard config/data/cache locations and `THRN_DATA_DIR` / `THRN_CACHE_DIR` behavior remain; no receipt, journal, or cache migration occurs. A missing, relative, ambiguous, or unsafe home fails closed. Secure directory handles inspect home components without following symlinks or Windows reparse points; the user skill root is derived from that validated root. No alternate destination fallback or arbitrary destination override is supported. Project receipt schema-v1/v2 JSON, deterministic v1 receipt keys, and project install/removal/update journal formats remain readable and unchanged. Explicit user receipts use strict schema v3 with `scope: user`, canonical user root and root filesystem identity, installed destination identity, complete provenance and SHA-256 inventory, a separate v3 content-digest domain, and a separate deterministic receipt-key domain/filename. User install intent exists only in its strict user install journal until no-replace commit captures destination identity; it is not published as an ownership claim. User receipts and user journals cannot be interpreted as project records, nor can project records authorize user ownership. Legacy receipts remain listable but do not gain ownership proof. User installation reuses the pinned catalog/source validation, archive validation, retained staging, collision checks, no-replace commit, receipt publication, install journal, and shared OS writer lock. User removal and update reuse full receipt/tree verification, destination identity, no-replace quarantine or backup, object-specific cleanup intents, no-replace receipt transition, and idempotent recovery. Check filters receipts by the explicit selected scope and its root and remains offline/read-only without creation or recovery. Existing unmanaged user skills and legacy Codex locations such as `$CODEX_HOME/skills` are never adopted or overwritten. Linux/macOS sync file and containing-directory entries where supported; Windows can flush file data but the current secure handle layer cannot portably flush directory entries. No cross-filesystem power-loss atomicity is claimed. Only the Codex adapter is supported; other agents remain future milestones. See [receipt design](receipts.md), [recovery protocol](recovery.md), and [security model](security-model.md). |
| ADR-016 | Typed Claude Code adapter reuses the scope-isolated secure skill lifecycle | Approved for M3-05 at `58f8fd962c7837bb5f1ca2fad965fbb5161ad897` | A typed `AgentId` and small adapter mapping identify Codex or Claude Code, supported project/user scopes, host-reserved skill names, exact destination layout, and destination validation. Codex remains `.agents/skills/<skillName>` in project and user roots. Claude Code uses `.claude/skills/<skillName>` in project and `~/.claude/skills/<skillName>` in user scope; agent selection stays explicit, and `--project` remains project-only. Official Claude Code [skills documentation](https://code.claude.com/docs/en/skills) identifies the project and personal skill roots and reserves names including `synced` and the `anthropic-skills` namespace. The [settings documentation](https://code.claude.com/docs/en/settings) says `CLAUDE_CONFIG_DIR` relocates settings, session history, and plugins; it does not document relocation of standalone skills. THRN therefore does not interpret it as a skill path override. No autodetection, automatic adoption, command-file migration, or skill execution is added. Claude install/remove/update journals use explicit schema v3 records that contain schema-v4 receipts; Codex project schema-v1/v2 receipts, Codex user schema-v3 receipts, old receipt keys, and old journal meanings remain unchanged. Claude schema-v4 receipts bind agent, scope, validated layout, canonical scope root and identity, installation-time destination identity, complete pinned source provenance, sorted inventory, per-file SHA-256 values, and deterministic ownership identity. The same resource is independently managed across Codex/Claude Code and project/user targets. Recovery holds the existing OS writer lock and verifies the original agent, scope, root, receipt, and filesystem identities before mutation; a lifecycle operation refuses to recover a pending transaction for another target. Existing no-follow inspection, no-replace commit/rename/publication, operation-owned quarantine and cleanup intents, complete-tree verification, and inert skill-content handling remain shared. Recovery is idempotent and preserves uncertain content. This does not claim cross-target atomicity: Windows directory-entry durability remains limited and cross-filesystem power-loss atomicity is not provided. Official Claude Code's public [repository](https://github.com/anthropics/claude-code) contains documentation/plugins but no CLI implementation source to independently inspect; implementation follows the official documentation contract above. No migration or authenticity claim is implied. |
| ADR-017 | Secure Cursor and Gemini CLI adapters with shared discovery compatibility | Approved for M3-06 at `d42a6aa` | Add `cursor` and `gemini` as explicit typed adapters over the existing validated install, check, update, removal, receipt, journal, lock, and recovery engine. Native destinations are `<project>/.cursor/skills/<skillName>` and `<home>/.cursor/skills/<skillName>` for Cursor, and `<project>/.gemini/skills/<skillName>` and `<home>/.gemini/skills/<skillName>` for Gemini CLI. The official [Cursor skills documentation](https://cursor.com/docs/skills) and [customization help](https://cursor.com/help/customization/skills) document compatibility with `.agents/skills` as well as Cursor-native roots; the native user Cursor path is used for cloud skill sync, while the shared `.agents/skills` path is not automatically synced to Cursor Cloud Agents. Cursor's documentation does not establish same-name precedence, so THRN rejects a same-named shared skill instead of guessing. Gemini CLI's official [skills documentation](https://geminicli.com/docs/cli/skills/) and [public repository](https://github.com/google-gemini/gemini-cli) document `.agents/skills` discovery and its precedence over `.gemini/skills` within a discovery tier; a same-named shared skill blocks native Gemini installation. Before a native install, a bounded no-follow read-only inspection classifies an explicitly targeted shared skill as a verified THRN-managed Codex skill, unmanaged skill, or absent path. THRN never adopts, moves, links, clones, overwrites, removes, or issues another ownership receipt for shared content. Existing Codex-managed shared content may already be discoverable, but its update and removal remain Codex-owned. New Cursor/Gemini receipts use strict schema v5, exact agent and scope, versioned destination layout, canonical scope root and filesystem identity, committed skill-directory identity, canonical resource ID and installed name, pinned GitHub provenance, complete sorted inventory, per-file lengths/hashes, and domain-separated deterministic identities. Cursor/Gemini install, removal, and update journals use schema v4 and bind their exact v5 receipt intent; existing Codex project schema-v1/v2, Codex user schema-v3, Claude schema-v4 receipts, prior journal versions, keys, and meanings are unchanged. Recovery remains under the OS writer lock and validates agent, scope, layout, receipt, destination identity, inventory, and object identities before mutation; cross-agent pending transactions cannot authorize one another. Read-only PATH capability inspection may report agent CLI binaries but does not enable automatic selection or infer that a destination is loadable. No shared ownership, migration, deduplication, or script execution is added. Linux/macOS sync supported file and directory metadata; Windows directory-entry durability remains limited by the secure handle layer, and no cross-filesystem power-loss atomicity is claimed. See [receipt design](receipts.md), [recovery protocol](recovery.md), and [security model](security-model.md). |
| ADR-018 | Explicit multi-agent installation with durable batch coordination | Proposed for M3-07; pending independent architectural review | `skills install` accepts repeated explicit `--agent` values in user-supplied order. One target retains the existing install path and output. `--no-input` never prompts or selects agents; explicit valid targets may proceed, while missing, duplicate, or invalid selections fail closed. One command uses exactly one explicit project or user scope; project scope remains the default, `--project` is project-only, and a batch cannot combine scopes. A deterministic target-conflict matrix is recorded and shown during dry-run. Codex together with Cursor or Gemini is incompatible when the shared `.agents/skills` path would be both installed and discovered as a competing copy; the pair is rejected before writes. Cursor and Gemini native targets can coexist when the complete per-target and shared-path preflight proves independence. A batch resolves one canonical catalog resource, fetches and validates its pinned source once, retains one staged inventory, and creates one immutable destination plan and receipt identity per selected agent. Under the existing application-data `.writer.lock`, the coordinator validates every target and then holds that single OS-backed reservation across all target commits; it does not reacquire the non-reentrant lock. Each child install continues using the existing no-follow, staging, no-replace, durable receipt, and target-journal engine. A separate strict schema-v1 batch-operation journal records a unique operation ID, canonical source and full commit pin, ordered agent identities and conflict matrix, exact scope root and destinations, root and preflight filesystem identity evidence, expected receipt identities, target commit/publication progress, verification outcomes, compensation state, and final batch outcome. Intent is durable before project mutation. A target failure stops later commits. Recovery first resolves matching child lifecycle journals under the already-held lock, then either finalizes forward when every target has its exact verified receipt and content or performs receipt-backed compensation in reverse target order. Compensation delegates to the existing verified removal/quarantine engine and never deletes a path on journal listing alone. Recovery is idempotent; uncertain receipts, parent identities, or content are preserved and leave a partial batch record for inspection. A target may be visible while later targets are still committing; there is no atomic cross-target commit or rollback. Linux/macOS synchronize supported files and directories. Windows directory-entry flush limitations and cross-filesystem power-loss limitations remain; the batch journal does not claim stronger platform durability. This scope adds no multi-agent update/removal, automatic selection, shared ownership, adoption, forced install, path deduplication, or new source types. See [receipt design](receipts.md), [recovery protocol](recovery.md), and [security model](security-model.md). |
