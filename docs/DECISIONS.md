|---|---|---|---|

| ADR-003 | External shell orchestration runs Git after agent exit, not model-side push | Approved | Separates implementation and credential-bearing Git operations |
| ADR-004 | Pin Rust 1.99.1 for initial foundation | Approved for bootstrap | Latest official stable patch as checked Nov 4, 2026 |
| ADR-005 | Curated static HTTPS catalog; exact GitHub commits | Specification | No dynamic backend or publisher ingestion |
| ADR-006 | Skills copied into agent target folders with durable receipts | Specification | Predictable cross-platform operations; ownership/recovery |
| ADR-007 | MIT source license for starter | Initial choice; review before first public release | Simple permissible option per specification |
| ADR-008 | Consider Unicode skill directory names in catalog `SkillName` | Proposed | The local M1-03 validator follows the current Unicode lowercase-alphanumeric name rule; the existing catalog type remains lowercase ASCII pending an explicit compatibility decision |
| ADR-009 | Classify metadata-empty DOS ZIP entries as regular files | Approved for M2-02 | The architect approved a narrow fallback: accept only `System::Dos`, zero external attributes, no directory marker, and `is_file() == true`. Staging writes these as ordinary non-executable files. Unix entries without type bits, symlinks, special files, and ambiguous directory metadata remain rejected. The exception matches ordinary files in the pinned GitHub `frontend-design` archive. |
| ADR-010 | Internal Codex directory commit uses platform no-replace rename | Approved for M2-04 at `bd66e51` | The internal commit engine prepares a private directory on the destination filesystem and requests Linux `renameat2(RENAME_NOREPLACE)`, macOS `renameatx_np(RENAME_EXCL)`, or Windows `SetFileInformationByHandle(FileRenameInfoEx)` with replacement disabled. It fails closed if the required primitive is unavailable. The architect accepted M2-04 at commit `bd66e51f7c33f2955ee068532f2cb4b59ab6b593`; the squash merge is `5c10d61516fbb692f096205a9a147be3ea6bd16f`. This provides complete-directory visibility and no-clobber at final commitment, not coordinated rollback or crash recovery. |
| ADR-011 | Schema-v1 Codex project receipts use deterministic path identity and canonical inventory digests | Approved for M2-05 at `fc2d92a` | Receipt filenames hash the length-prefixed canonical project path, agent, and canonical resource ID under a domain separator. Strict JSON records include the distinct skill directory name, source provenance, project filesystem identity, complete bounded sorted file/directory inventory, and a domain-separated SHA-256 digest with explicit path and file-length boundaries. Storage uses exclusive temporary files, an exclusive writer reservation, no-replace publication, no-follow reads, and supported durability synchronization. Receipts are ownership claims, not publisher authenticity or deletion authorization. See [receipt design](receipts.md). |
| ADR-012 | Internal installs use an append-only operation journal and OS-backed store lock | Approved for M2-06 at `a711b522f6c8a7db221ac43cfd281788e25d1f91` | A versioned application-data journal records operation identity, strict schema-v1 receipt intent, destination/staging filesystem identities, operation-created inventory, and ordered state transitions. Recovery opens the receipt store, acquires and validates the persistent `.writer.lock`, and only then reads bounded journal snapshots; the lock remains held through recovery and result determination. Installation admission also reads and validates journals under its reservation lock and fails closed if any operation remains after the preceding recovery attempt. The reservation stays held through preparation, project commit, receipt publication, and journal cleanup. Recovery trusts neither receipt nor journal alone, verifies exact identities and hashes, and preserves uncertain content. Windows directory-entry flush limitations and lack of cross-filesystem power-loss atomicity are explicit. M2-07 exposes this approved boundary only through Codex project installation; remove and update remain out of scope. See [recovery protocol](recovery.md). |
| ADR-013 | Receipt-backed Codex project skill removal requires installation-time destination identity | Proposed for M3-01; pending independent architectural re-review | New installations use backward-compatible receipt schema v2, which requires the final committed destination volume/object identity and binds it into the versioned content digest. The install operation journal remains schema v1 and starts with the existing v1 receipt intent; after no-replace commit it durably advances to a v2 receipt only while recording the identity obtained from the secure destination handle. No v2 receipt is published and no install success is reported before that snapshot. Existing schema-v1 receipts remain byte-for-byte unchanged and listable, but automatic removal refuses them; THRN never derives missing ownership from a directory observed during removal. Existing interrupted install journals remain readable under their original identity and inventory checks, and recovery never rewrites an already-published v1 receipt. Removal requires v2 evidence, verifies it before quarantine planning, and revalidates the same identity at every destructive boundary. A separate versioned removal record captures the receipt, parent, destination, and per-object identities before mutation; records state transitions and per-object cleanup intents; moves the destination to operation-private sibling quarantine with no-replace rename; removes only verified receipt-listed files and empty recorded directories; and retires the receipt after content removal is established. Recovery rolls back only before deletion begins and only if the full original tree is intact; after any cleanup intent it advances only when every remaining object is still provable. Nonterminal legacy removal journals lacking install-time evidence fail closed and remain preserved. The existing `.writer.lock` serializes installation, removal, and recovery through completion. Windows directory-entry metadata cannot currently be flushed with the existing handle layer; no cross-filesystem/power-loss atomicity is claimed. See [receipt design](receipts.md) and [recovery protocol](recovery.md). |
| ADR-014 | Receipt-backed Codex project skill update uses a separate journal, old-version backup, and no-replace receipt transition | Proposed for M3-02; not approved | Update accepts one exact canonical catalog ID only when a schema-v2 receipt proves the same Codex project installation and the complete live inventory, file identities, lengths, and hashes verify. The validated local catalog must retain the same resource ID, GitHub owner/repository, source directory, and installed skill name, and pin a different full commit. No catalog refresh or caller-supplied source is used. A typed immutable `UpdatePlan` captures the old receipt/installation proof, replacement stage inventory, file-level diff, intended stage/backup paths, commit-time assumptions, and receipt transition including the old receipt file identity and raw-byte digest. A distinct schema-v1 update journal in application-data `updates` records both inventories and directory identities, old/new receipt contents, receipt temp/backup identities, operation-owned names, states, and per-object cleanup intents. Under the shared OS-backed `.writer.lock`, THRN stages the complete replacement beside the destination, rehashes it, records its identity, moves the verified old tree to an operation-owned backup with a no-replace rename, and commits the replacement to the original destination with a second no-replace rename. This is not an atomic swap. The receipt filename remains deterministic and common to old/new versions. THRN preserves the exact old receipt in a no-replace operation backup and publishes the new schema-v2 receipt through the existing no-replace publication API; unchecked receipt overwrite is prohibited. Installed listing holds the lock while reading and fails closed while any lifecycle journal is pending, preventing display of an incomplete receipt transition. Recovery is idempotent and verifies full trees, object IDs, raw receipt bytes, active receipt, and destination identity. A `Prepared` record may terminate as rolled back only when the old install/receipt remain exact and no stage/backup exists; once replacement staging has a journaled identity recovery proceeds forward. Before cleanup, a future implementation could add verified rollback only if old backup and replacement can both be positively identified; this implementation chooses forward recovery. After any old-backup cleanup intent, only strict forward recovery is allowed; missing objects require their matching durable cleanup intent. Recovery never adopts a directory from matching hashes alone or recursively deletes a backup. The old receipt is retained until the new tree/receipt verify and old-tree cleanup is complete, then removed under its own durable cleanup intent. A crash after receipt publication but before the next journal snapshot is recoverable only when the new receipt identity/contents and old backup match the journal; an unrecorded receipt temp is preserved and requires inspection. Linux/macOS synchronize files and containing directories where supported. Windows directory-entry metadata cannot currently be flushed through the secure handle layer, and no cross-filesystem power-loss atomicity is claimed. See [receipt design](receipts.md) and [recovery protocol](recovery.md). |

Proposed changes require explicit architect approval, with evidence and migration implications. A coding agent may record a proposal but must not silently change an approved decision.
