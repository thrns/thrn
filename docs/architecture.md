# Architecture

## Current implementation

THRN is one Rust binary crate (`thrn`). The executable starts in `src/main.rs`, which calls the CLI and converts its result to a process exit code. `src/cli.rs` defines the Clap parser and dispatches `doctor`, offline skill discovery and listing, explicit catalog refresh, installed-listing checks, local skill validation, and the read-only install dry-run. `src/registry/remote.rs` performs the fixed HTTPS catalog request and exposes a bounded stream; `src/registry/catalog.rs` remains the sole catalog JSON validator; `src/registry/cache.rs` reads and atomically replaces the validated cache envelope; and `src/registry/catalog_service.rs` selects cache or bundled data and computes freshness. `src/registry/discovery.rs` builds an exact ID/alias index and performs stable text search, which the catalog listing reuses for canonical-ID ordering. The source pipeline is split into `src/sources/github.rs` for pinned HTTPS fetches, `selection.rs` for exact manifest-root and catalog-path matching, `staging.rs` for private extraction and lifetime ownership, and `archive.rs` for M2-01 ZIP validation. `src/install/plan.rs` builds an immutable proposal from validated stage metadata, `inventory.rs` verifies staged files against the archive manifest and records SHA-256 digests, `destination.rs` captures a no-follow destination snapshot, and `command.rs` coordinates planning. `commit.rs` owns the validated stage together with its plan and performs the internal M2-04 Codex project copy and no-replace directory commit; the CLI does not call it. `src/install/receipt.rs` validates schema-v1 ownership records and canonical inventory digests; `receipt_store.rs` reads existing receipts without creating storage and publishes validated receipts only after the internal commit capability confirms success. `src/skills/validator.rs` reads and validates only a local skill's `SKILL.md`. `src/error.rs` carries CLI, catalog, install-planning, receipt-discovery, resolution, validation, and output-I/O errors to the process boundary.

The runtime dependencies are intentionally small:

| Dependency | Current use |
|---|---|
| `clap` with `derive` | Typed command parsing and generated help/version/usage responses. |
| `serde` with `derive` | Strictly decode the external catalog schema into private raw parsing records. |
| `serde_json` | Bounded JSON decoding for the version-1 catalog parser. |
| `crc32fast` | Recheck staged regular-file bytes against the CRC values already verified by the archive validator. |
| `ring` | Compute staged and copied-file SHA-256 digests and generate private staging names from the system random source. |
| `rustix` (Linux/macOS only) | Open project paths relative to no-follow directory handles and use the platform's atomic no-replace rename primitive. |
| `windows-sys` (Windows only) | Use reparse-point-aware handles and `FileRenameInfoEx` with replacement disabled. |
| `serde_path_to_error` | Add a schema field path to type errors so diagnostics can identify the location without echoing rejected JSON values. |
| `serde-saphyr` (deserialization only) | Parse bounded YAML frontmatter with duplicate-key, alias, merge-key, document, nesting, and unknown-tag controls. |
| `ureq` with only `rustls` enabled | Blocking HTTPS transport with certificate verification. Compression and unrelated HTTP features stay disabled; the client has explicit connect, body, and overall timeouts and follows no redirects. |
| `zip` with defaults disabled and only `deflate-flate2-zlib-rs` enabled | Parse ZIP metadata and stream Stored/Deflate entries for bounded size and CRC validation. Encryption and unrelated compression codecs are not compiled. |
| `directories` | Resolve standard per-user cache and application-data locations through XDG, macOS, and Windows conventions. |
| `tempfile` | Create a private temporary cache file beside the destination and atomically replace the cache where supported. |
| `thiserror` | Typed CLI-boundary errors for Clap, validation, and standard I/O failures. |
| `libc` (Unix only) | Set `O_NOFOLLOW` when opening `SKILL.md`; Windows uses the standard library's reparse-point flag. |

The standard library supplies process handling, environment constants, output, and validation collections. `Cargo.lock` records resolved crate versions. `ureq` 3.5.1 was selected as the maintained blocking client: Cargo reports Rust 1.85 as its MSRV, below THRN's Rust 1.99.1 minimum. The lockfile currently resolves its `rustls` feature and root certificates; defaults are disabled so gzip and other unused features are not compiled. The archive reader is `zip` 9.4.0, whose Rust 1.88 minimum is below THRN's Rust 1.99.1 toolchain. Default features are disabled and only the zlib-rs-backed Deflate feature is enabled. The validator supports Stored and Deflate compression methods.

The YAML parser is `serde-saphyr` 2.1.1, which declares Rust 1.89 as its MSRV; THRN pins Rust
1.99.1. Only the `deserialize` feature is enabled, with the crate's defaults disabled, so
serialization, comment capture, property interpolation, and `!include` support are not compiled
in. Its 2.1.1 release includes an empty-document parsing fix; its parser provides configurable
budgets and rejects duplicate mapping keys by default. THRN additionally sets explicit limits and
strict tag and merge-key policies for frontmatter.

## Current boundaries

`--help`, `--version`, `doctor`, `skills list`, `skills list --installed`, default `skills search`, `skills info`, and `skills validate` work offline. `skills search --refresh` calls the catalog transport and writes the cache. It uses one fixed HTTPS endpoint, verifies certificates, does not follow redirects, applies timeouts, and caps streamed catalog bytes at 1 MiB. All catalog network data passes through the M1-01 parser before selection or persistence. `skills install --dry-run` reads the catalog cache or bundled metadata without refreshing it, then calls the M2-02 source API for the exact pinned skill archive. The source API accepts only a validated catalog `Resource`; it validates streamed ZIP bytes before extraction, selects one exact catalog path, and returns a privately staged `StagedSkill`. Its narrow DOS ZIP compatibility rule accepts only DOS entries with zero external attributes, no directory marker, and `is_file() == true`; staged files are always non-executable. M2-03 rechecks the exact staged inventory and inspects the Codex project destination without writes. The internal M2-04 session keeps that stage alive with its immutable plan, revalidates source and target assumptions, copies only inventoried files to a destination-local private directory, verifies byte counts and SHA-256 digests, and commits the directory atomically without replacing an existing object. No CLI command invokes the commit-and-receipt engine; non-dry-run install remains rejected until M2-06 recovery is implemented. Automated tests inject network responses, temporary-directory locations, destination inspection failures, and installation filesystem failures; they use generated ZIPs and do not contact GitHub.

## Current and planned boundaries

Implemented boundaries:

- **M1-01:** `src/models/catalog.rs` contains validated catalog identity types; `src/registry/catalog.rs` parses bounded schema-v1 JSON without network or filesystem access. `docs/registry.md` documents the accepted schema and limits.
- **M1-02:** `src/registry/discovery.rs` builds exact canonical-ID and explicit-alias lookup indexes from validated records, and performs stable text search over the compile-time bundled catalog. The CLI exposes `skills search` and `skills info` without network access or skill downloads.
- **M1-03:** `src/skills/validator.rs` validates a local `SKILL.md` using bounded YAML parsing and typed frontmatter checks. It does not inspect supporting files, write files, or execute skill content.
- **M1-04:** `src/registry/remote.rs`, `cache.rs`, and `catalog_service.rs` separate HTTPS transport, persistent cache, and local-source/freshness selection. Default discovery uses a validated cache or bundled metadata without network access; only `--refresh` contacts the fixed endpoint.
- **M1-05:** `skills list` reuses `CatalogService` and `CatalogResolver` to show catalog availability in canonical-ID order. `skills list --installed` reads only the OS application-data receipt directory, with missing/empty storage reported as an empty managed-installation list. M2-05 adds the versioned schema and writer described below.
- **M2-01:** `src/sources/archive.rs` validates ZIP entry names, type metadata, collisions, resource budgets, local/central header consistency, expanded byte counts, and CRCs. Its manifest preserves the full archive-root prefix and contains metadata only.
- **M2-02:** `src/sources/github.rs`, `selection.rs`, and `staging.rs` implement pinned HTTPS fetching, one exact GitHub-to-codeload redirect check, manifest-based root and source-path selection, and isolated staging followed by M1-03 metadata validation. The pinned `frontend-design` archive passes the validator and staging pipeline with the approved DOS metadata fallback. Staged content stays owned by the returned `StagedSkill`; its `TempDir` guard attempts cleanup when dropped. This API does not install content or execute it. See [the source-fetch and staging boundary](security-model.md#m2-02-pinned-github-fetch-and-staging-boundary).
- **M2-03:** `src/install/inventory.rs` validates a complete bounded staged-file and directory inventory against M2-02's selected archive manifest and rechecks file sizes and CRC-32 values. `destination.rs` requires an existing project root and inspects `.agents/skills` with no-follow metadata checks, recording symlinks, unsupported objects, case-insensitive collisions, and existing skill paths as conflicts. Each inspected destination directory is capped at 16,384 entries. `plan.rs` is a pure builder over the validated stage inventory and destination snapshot; `command.rs` uses `CatalogService::discover()` and the injected M2-02 source boundary to print one complete plan. This command may contact GitHub to fetch pinned files, but it never refreshes the catalog or modifies the project. The plan records assumptions for a later pre-write recheck; it is not install authorization. See [the M2-03 planning boundary](security-model.md#m2-03-immutable-plan-and-read-only-dry-run).
- **M2-04:** `src/install/commit.rs` is an internal-only Codex project adapter and install session. It keeps `StagedSkill`, the validated inventory, and immutable `InstallPlan` alive together; it checks that their source identities and intended `<project-root>/.agents/skills/<skillName>` destination agree. It revalidates source bytes and destination listings/identities before writes and before final commitment, creates each missing parent exclusively, stages on the target filesystem, copies only planned regular files, compares byte counts and SHA-256 digests, and discards executable permissions. Linux uses `openat`/`O_NOFOLLOW` and rustix's `renameat2(RENAME_NOREPLACE)`; macOS uses rustix's `renameatx_np(RENAME_EXCL)`; Windows uses reparse-point-aware handles and `SetFileInformationByHandle(FileRenameInfoEx)` with zero flags and a fully qualified target path, which disables replacement. Unsupported no-replace behavior fails closed. The final directory rename provides atomic visibility on supported local filesystems, not a durable transaction or crash recovery. The CLI still requires `--dry-run`; M2-04 creates no receipts and does not enable public installation. See [the M2-04 internal installation boundary](security-model.md#m2-04-internal-prepared-and-committed-directory-installation).
- **M2-05:** `src/install/receipt.rs` defines strict schema-v1 ownership and file-integrity records. Receipt identity is a domain-separated SHA-256 over length-prefixed canonical project path, agent, and canonical resource ID; the installed `skillName` remains distinct. A second domain-separated SHA-256 covers a sorted inventory with explicit directory/file tags, path lengths, file lengths, and raw per-file digests. `receipt_store.rs` reads without creating storage, rejects linked/unknown/corrupt/conflicting records, reserves claims before the internal commit, then publishes only after an opaque successful-commit capability verifies the exact destination tree. Receipt JSON uses exclusive temporary files, file sync, read-back validation, and platform no-replace publication; Unix also syncs containing directories, while Windows parent-directory durability is limited by available APIs. `skills list --installed` displays validated records and says current content integrity was not checked. It never fetches the catalog or accesses project paths. The internal boundary is not called by CLI; receipt persistence failure after directory commit is explicitly incomplete, with no speculative deletion. M2-06 owns coordinated rollback and crash recovery. See [the receipt design](receipts.md).

Future design boundaries, not current modules or capabilities:
- **M2-06:** rollback and crash recovery for interrupted or failed installation sequences.
- **M3:** user scope, agent discovery, and receipt-backed check/update/remove operations with conflict handling.

The specification's long-term module map (`cli`, `models`, `registry`, `sources`, `skills`, `agents`, and `install`) is guidance for tested slices. Do not create empty modules to match that map. Command parsing and dispatch stay in the CLI layer; validation, source access, and filesystem transactions belong in their eventual domain boundaries.

Catalog source paths are validated lexically only. The parser does not establish whether a source exists or whether its content can be extracted safely; those checks belong to later fetching and installation slices.

## Adding commands

Add a Clap command variant and a small dispatch arm in `src/cli.rs`; put domain behavior in a module only when the slice needs it. Keep parsing separate from filesystem transactions. Preserve offline help/version behavior, successful output on stdout, diagnostics on stderr, and the existing `0`/`1`/`2` exit conventions documented in [the CLI contract](cli.md). Add integration coverage for the real executable's status and output channels, including offline operation. Never execute retrieved skill content as part of command dispatch.
